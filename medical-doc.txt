B2B MEDICAL STORE APP – AI DEVELOPMENT SPECIFICATION

Project: MedStore B2B
Frontend: Ionic + Angular (latest)
Backend: Node.js + Express + Mongoose

USER ROLES:
- Store Owner: Full access (create/assign orders, manage users, clients, items, reports)
- Sales Person: Create orders, POS, deliver orders, record payments, collect dues

CORE WORKFLOWS:

1. Order Creation (Sales Person/Owner):
   - Select/add client
   - Add items one by one
   - System checks: in stock → reduce stock / low stock → alert / out of stock → backorder / not existed → create placeholder + backorder
   - Backorder creates alert for owner
   - Order status = "created"

2. Order Assignment (Owner only):
   - Owner assigns order to Sales Person for specific task:
     a) For "delivery" → Sales Person delivers items
     b) For "payment_collection" → Sales Person collects due
   - Status = "assigned"
   - Can reassign to different Sales Person if needed

3. Delivery & Payment (Assigned Sales Person):
   - Mark order as delivered (isDelivered: true, deliveredAt: timestamp)
   - Record payment: full → completed / partial → due remains / zero → borrow
   - Update client total due
   - If due zero → order completed

4. Due Collection (Assigned Sales Person):
   - Sales Person visits client to collect outstanding due
   - Record payment: full → dueCollected: true → order completed
   - Partial payment updates dueAmount
   - Can record multiple payments for same order

5. POS (In-Store):
   - No assignment needed
   - Add to cart, pay immediately
   - Stock reduces instantly
   - Order completed right away
   - Print bill or send digital invoice

6. Backorder Management (Owner):
   - Owner monitors backorder alerts
   - When items arrive: mark "backorder-purchased"
   - Update stock levels
   - Order ready for delivery

ALERT SYSTEM (Auto checks every 6 hours):

- Low stock (≤10) → warning alert
- Out of stock (0) → urgent alert
- Expiring soon (≤30 days) → warning alert
- Expired (< today) → urgent alert
- Backorder pending → warning alert (owner only)

DATABASE MODELS (Mongoose Schemas):

User: name, email, password, phone, role, business, assignedClients[], isActive, stats (server-calculated)
  - business: ObjectId reference to Business (required for sales_person, optional for owner)
  - assignedClients: Array of Client IDs assigned to sales person (empty for owner)
  - stats: Server-calculated object containing:
    * totalOrders: Total orders count
    * completedOrders: Completed orders count
    * pendingOrders: Pending orders count
    * totalRevenue: Sum of all order amounts
    * totalDueCollected: Sum of paid amounts
    * pendingDueAmount: Sum of outstanding dues
    * averageOrderValue: Total revenue / total orders
    * completionRate: (completedOrders / totalOrders) * 100
    * collectionRate: (totalDueCollected / totalRevenue) * 100

Business: name, owner, country, phone, address, logo, website, businessLicense, isActive (multi-tenant root)
  - owner: Reference to User (owner role)
  - Central entity that scopes all other data for multi-tenancy
  - One owner can manage one business
  - All data (clients, items, orders, alerts) belongs to a specific business

Client: name, phone, email, address, totalDue, creditLimit, address, shopName, business (multi-tenant)
  - REMOVED: assignedSalesPerson field (no longer stored on Client)
  - Virtual field 'salesPerson': Joins User where client._id is in User.assignedClients array
  - Relationship management: Now via User.assignedClients array (one-to-many pattern)
  - Benefits: Cleaner model, no data duplication, dynamic access control

Category: name, description, isActive, business (multi-tenant scope)
  - business: Reference to Business for multi-tenant isolation
  - Categories are business-specific

Item: name, category, stockQuantity, lowStockThreshold, expiryDate, sellingPrice, costPrice, sku, isExpired, description, business (multi-tenant scope)
  - business: Reference to Business for multi-tenant isolation
  - Each item belongs to a specific business

Order: orderNumber, orderType, client, createdBy, assignedTo, assignedFor, assignedAt, isDelivered, deliveredAt, dueCollected, dueCollectedAt, items[], subtotal, discount, totalAmount, paidAmount, dueAmount, paymentStatus, orderStatus, payments[], business (multi-tenant scope)
  - business: Reference to Business for multi-tenant isolation
  - All orders scoped to a business

Alert: type, itemId, orderId, message, severity, seenByOwner, seenBySalesPerson, resolved, business (multi-tenant scope)
  - business: Reference to Business for multi-tenant isolation
  - Alerts are business-specific

KEY ORDER FIELDS:
- assignedTo: ID of Sales Person assigned
- assignedFor: "delivery" or "payment_collection"
- assignedAt: When assigned
- isDelivered: Whether items delivered
- deliveredAt: Delivery timestamp
- dueCollected: Whether due fully collected
- dueCollectedAt: Collection timestamp
- orderStatus: "created" | "assigned" | "completed" | "backorder"

MULTI-TENANT ARCHITECTURE ✅

The application is built as a true multi-tenant system where each Business is a completely isolated tenant.

Business Model Structure:
  {
    _id: ObjectId,
    name: "MedStore Pharmacy",
    owner: ObjectId (User reference),
    country: "Pakistan",
    phone: "03001234567",
    address: "123 Main Street, Karachi",
    logo: "url_to_logo",
    website: "www.medstore.pk",
    businessLicense: "12345",
    isActive: true,
    createdAt: Date,
    updatedAt: Date
  }

Multi-Tenant Data Flow:

1. AUTHENTICATION:
   - User logs in with email/password
   - JWT token generated with: { id, email, role, business }
   - business field is the tenant identifier
   - req.user.business used for all data filtering

2. QUERY FILTERING:
   - Every query includes: { business: req.user.business }
   - Prevents data leakage between businesses
   - Applied at model level for consistency
   
   Example:
   ```typescript
   // Get clients for current user's business only
   const clients = await Client.find({
     business: req.user.business,  // ← Multi-tenant filter
     isActive: true
   });
   ```

3. ROLE-BASED MULTI-TENANCY:
   
   OWNER:
   - Can only access data from their own business
   - Cannot see other businesses' data
   - jwt.business identifies their business
   - Has full control over their business
   
   SALES_PERSON:
   - Must be assigned to a specific business
   - user.business = their business tenant
   - Can only see clients assigned to them
   - user.assignedClients restricts further access
   - Cannot see other businesses' data

4. DATA ISOLATION GUARANTEES:
   
   ✅ Business Field Index:
   - Every model has index on business field
   - Fast filtering by tenant
   - Prevents N+1 queries
   
   ✅ Query Validation:
   - All routes check req.user.business exists
   - Return error if business missing
   - Prevents accidental global access
   
   ✅ Cross-Business Prevention:
   - Cannot access client from business A with user from business B
   - Cannot create order for client outside business
   - Cannot assign sales person from different business
   
   Example:
   ```typescript
   // Verify client belongs to current business
   const client = await Client.findById(clientId);
   if (client.business.toString() !== req.user.business.toString()) {
     return errorResponse(res, "Client not found", 404);
   }
   ```

5. ASSIGNMENT BOUNDARIES:
   
   ✅ Sales Person Assignment:
   - Sales persons can only be assigned clients from their business
   - Cannot assign across businesses
   
   ✅ Order Creation:
   - Orders inherit business from client
   - Cannot create order for client outside business
   
   ✅ Item Assignment:
   - Items belong to business
   - Categories belong to business
   - Cannot cross-reference between businesses

6. MULTI-TENANT QUERIES:

   Get Clients (Multi-tenant filtered):
   ```typescript
   const clients = await Client.find({
     business: req.user.business,
     isActive: true
   });
   ```

   Get User's Assigned Clients (Multi-tenant + role-based):
   ```typescript
   if (req.user.role === "sales_person") {
     const user = await User.findById(req.user.id);
     const assignedClientIds = user.assignedClients;
     const clients = await Client.find({
       business: req.user.business,  // ← Tenant isolation
       _id: { $in: assignedClientIds }  // ← Role-based filtering
     });
   }
   ```

   Get Orders (Multi-tenant + role-based):
   ```typescript
   let query = { business: req.user.business };  // ← Tenant filter
   
   if (req.user.role === "sales_person") {
     query.$or = [
       { createdBy: req.user.id },      // ← Only their orders
       { assignedTo: req.user.id }      // ← Assigned to them
     ];
   }
   
   const orders = await Order.find(query);
   ```

7. AGGREGATION WITH MULTI-TENANCY:

   Client Options Aggregation:
   ```typescript
   pipeline: [
     {
       $match: {
         isActive: true,
         business: req.user.business  // ← Tenant filter first
       }
     },
     {
       $lookup: {
         from: "users",
         pipeline: [
           {
             $match: {
               business: req.user.business,  // ← Tenant filter
               $expr: { $in: ["$$clientId", "$assignedClients"] }
             }
           }
         ],
         as: "assignedSalesPerson"
       }
     },
     // ... rest of pipeline
   ]
   ```

CRITICAL BUSINESS RULES:

1. When creating order:
   - Existing item with stock → reduce stock immediately
   - Existing item insufficient stock → mark backorder, create alert
   - Item not exist → create placeholder (stock 0), mark backorder
   - POS order → completed immediately
   - Owner can create orders for any client
   - Sales Person can only create for assigned clients

2. Order Assignment (Owner only):
   - Owner assigns order to Sales Person with task type:
     a) assignFor: "delivery" → Sales Person delivers items
     b) assignFor: "payment_collection" → Sales Person collects due
   - Updates: assignedTo, assignedFor, assignedAt
   - Order status → "assigned"
   - Sales Person can execute assigned task and record updates

3. Order Delivery (Assigned Sales Person):
   - Mark order as delivered: isDelivered: true, deliveredAt: timestamp
   - Can record payment immediately or later

4. Due Collection (Assigned Sales Person):
   - Collect outstanding due from client
   - Record full/partial payment
   - If due fully collected: dueCollected: true, order → "completed"

5. When recording payment:
   - Add to paidAmount, recalculate dueAmount
   - Update paymentStatus: 0 paid = borrow / partial = partial / full = fully_paid
   - If fully paid → orderStatus = completed
   - Update client.totalDue = sum of all dueAmounts

6. Backorder items purchased (owner action):
   - Mark purchased = true
   - All purchased → isBackorderComplete = true
   - Order ready for delivery

7. Background jobs:
   - Every 6 hours: check low stock & out of stock → create alerts
   - Daily at midnight: check expiry → create alerts, mark expired items

Summary of What the App Does (One Paragraph)

A B2B mobile app for medical stores where store owners manage the business with full control over orders and users, while sales persons handle order creation, POS billing, delivery, and payment collection. Owners create orders for any client and can assign them to sales persons for delivery or payment collection tasks. The system automatically checks stock and expiry, creates alerts for low/out-of-stock or expiring items, and supports backorder for missing items. Sales persons deliver orders, record full/partial/borrow payments, and collect dues on assigned orders. Owners manage users, clients, items, and view comprehensive reports on outstanding dues, collections, sales person performance, stock status, and expiry items. No customer app – all orders are staff-initiated with role-based workflows.
